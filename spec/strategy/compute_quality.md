# compute_quality — 提高日批计算效果

> 历史参考：当前方案与待办已合并至[策略研究与实施方案](plan.md)。下文保留原日期记录；“方案被替代”不代表功能已验收。

> 2026-09-08；状态：优化与验收方案待实施，不代表已有性能测量或策略收益改善。
> 日批目标见[daily_batch.md](daily_batch.md)；分别评价数值正确、计算效率、结果可用性和策略增益。

## 1. 优先级与评价方式

| 顺序 | 要改善的效果 | 证据 | 不可替代的边界 |
|---|---|---|---|
| 1 | 算得正确 | 日期/价格/股数/现金对账、C1～C8及缺数反例 | 不能用更快掩盖未来信息和虚构成交 |
| 2 | 每天能及时交付 | 数据就绪率、截止内发布率、失败/晚到原因 | 不靠忽略缺数据或省略风控凑准时 |
| 3 | 减少重复和资源占用 | 分阶段耗时、处理行数、缓存命中与RSS、DB锁等待 | 增量计算必须与相同快照的全量结果等价 |
| 4 | 策略有独立增益 | 同账户基准、成本后样本外、尾部损失与参数邻域 | 不把高胜率、更多交易或低现金当唯一成功 |

缺数据造成的“无结果”和行情不满足造成的“无机会”分别计数；不能为了提高产出率每天强推两只。
已有计算错误按[实现审查](implementation_review.md)优先修复，日批迁移不免除这些验收。

## 2. 共享输入，分开账户

| 计算层 | 计算范围/频率 | 复用与失效规则 |
|---|---|---|
| 全市场底层 | 日增量行情、完整性、金额；按正式日历推进 | 同快照只读/聚合一次，排名分母始终全市场 |
| 公共特征 | 全市场MA20宽度、指数趋势、启用的情绪统计 | 按交易日、输入快照与公式版本保存 |
| 月度股票池 | 每日维护月内金额；完整月终确定Top20 | 月内部分累计不能替代上个完整月正式名单 |
| 证券特征 | 当前Top20、旧仓和未完成退出的必要历史 | MA/ATR/前高等滚动更新，共享同版本特征 |
| 策略候选 | 已启用家族的信号、排序和缺失理由 | 相同数据/参数可复用；账户资格过滤仍保留 |
| 账户组合 | 每个生效账户的现金、持仓、风险和条件数量 | 不复用其他本金的成交/高水位或缩放旧账本 |
| 报告与解释 | 已校验数值包、图表序列、下载件 | 绑定run和结果hash；读取只返回已保存产物 |

滚动窗口不是简单取最近N条：保留日历、缺失标记、前收与必要预热，停牌不能压缩历史。
变更检测必须能发现历史修订；重算受影响的滚动窗口及依赖，递归指标须追到可靠检查点。
修订形成新版本，不覆写已发布决策；仅保存hash却无法还原源记录，不构成可重演快照。
首次建库/回补使用分块全量，常规日批使用增量；不能为省CPU丢掉退市股或未进入Top20的排名记录。

## 3. 一套确定性核心，日批与回测共用

抽取“截至某决策点的输入 + 前一账户状态 → 指标/意图/下一状态”的确定性接口。
日批输入固定截止快照；回测按历史时钟逐日提供相同结构，后续执行/回填按独立时点发生。
禁止维护一份前端计算、一份夜间公式、一份回测公式；解释层只读取结果，不能决定股数。
排序、边界取整、缺失处理、费用精度和随机参考种子明确版本，重跑得到一致输出。
现金和股数必须一致；特征浮点容差预先定义，近阈值变化须定位，不允许容差改变交易分类。
新增增量算法先与独立全量参考比较，覆盖窗口交界、复权修订、缺日、换月和代码身份变化。
原模型按未知开盘缩量而新日批固定数量时，执行模型单独对照；共享指标不等于成交模型已等价。

## 4. 调度、查询与内存

优先复用现有quant内部调度/队列，任务分类与优先级先写契约；调度器不直接持库跑计算。
依赖顺序为必要ETL就绪→日批→发布；历史回补/研究任务采用较低优先级，不能堵住当前日数据。
单并发起步；长研究任务按安全检查点让出执行权，日批到期前停止领取长研究块。
作业取消/重启与检查点账本一致，不能为抢占导致重复记账；研究让出后继续使用原输入版本。
仍遵守SQLite单属主、单连接和锁边界：短批读取后释放锁，在Go内存计算，再分批写入结果。
避免逐证券逐日期重复SQL、窗口重复构造整个指数map、报告查询时扫描全行情事实表。
预备计算只有在最终输入版本一致时才可采用；新增记录或修订导致依赖失效就重算相应部分。
缓存键至少包含数据、证券/账户、策略/公式、执行/费用、日期和窗口，不能仅凭日期命中。
先用EXPLAIN与剖析确认瓶颈，再调整索引或批大小；不预设换数据库、加服务或提高并发。

## 5. 工程验收初值

以下是待测目标，不是当前服务能力或外部数据到达承诺。

| 项目 | 初值/方法 |
|---|---|
| 发布时限 | 沿用22:00截止，默认23:00前发布完整包或明确阻断/失败状态 |
| 日批计算耗时 | 分别计队列等待、取数、特征、组合、校验、发布；先测代表性样本再冻结预算 |
| 结果读取 | P95<500ms；响应规模、机器与并发固定，性能验证不包含暗中计算 |
| 内存 | quant进程遵守现行<400MB红线；并计ETL、索引/缓存和日批，不只测单函数 |
| 研究规模 | 沿用tuning.md参数/账户/子任务上限；夜批优先，不在每天批次全历史调优 |
| 增量一致性 | 对相同快照逐日期比较参考全量，交易分类/股数/现金一致 |
| 运维指标 | 发布有效率、缺数阻断率、延迟发布率、重试/重复任务数、读取触发计算次数 |

发布有效率分母为应有交易日，数据阻断不能隐藏；另外报告“数据已就绪时”的计算准时率。
首轮用普通交易日、换月日、回补/修订日和ETL繁忙时段；20个交易日观察只能验证运行表现。
超预算先定位来源延迟、锁等待或计算热点，不能把它们统称“回测慢”或把失败期剔除。
资源基线见[ops/jarvis-sh](../ops/jarvis-sh.md)，数据时钟见[quant/publish](../backend/quant/publish.md)。

## 6. 提高策略效果的反馈闭环

每天保存市场状态、候选、有效信号、预算拒绝、计划和实际回填，事后才能分析机会损失位置。
每周检查数据/执行偏差，每月看资金利用、行业集中和失败突破；这些观察不自动触发调参。
先比较S0/S1/S2/F1在同一日批时钟与执行模型下的增量，再根据问题选择一次E1/E2/E3或S3实验。
固定家族后只用预登记3×3空间；开发/验证/测试隔离，日批仅读取已采用参数版本。
选择稳定邻域并报告成本和尾部风险；缺乏稳定增量则保留现版，收益目标未达不扩大搜索。
研究看板和日常结果都保留数据日期及模型版本，不能把新规则的历史曲线当成旧日已经生成的建议。
采用与回退保留旧仓、名额、现金和风险状态；年度达成与重叠窗口的解释沿用validation.md。

## 7. 实施验收必须补的反例

1. 连续刷新/导出、无缓存、无今日结果，均不能触发计算；研究提交只入队。
2. 同批多账户共享特征但不共享现金/股数；截止后改本金不改当前已发布结果。
3. 全市场漏一天、月末迟到、复权因子修订、旧仓离池受困，增量与全量的状态保持一致。
4. 两个重复批次、发布一半失败、进程重启、研究取消/让出，结果版本和账本没有重复或混用。
5. 日批当时可见的结果不含未来开盘；回测必须还原截止与数量规则，后验价格另用于执行核验。
